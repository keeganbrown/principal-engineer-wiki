# Quiz: Influencing Without Authority

## A principal engineer wants every service to adopt structured logging. Which approach fits the wiki's advice?

- [x] Gather incident stories, frame it as incident time, build a library with one eager team, and let them show results.
- [ ] Write a memo mandating structured logging by the end of the quarter.
- [ ] Ask the VP of engineering to order every team to adopt it.
- [ ] Open pull requests against every team's service without asking first.

**Why:** Listen first, frame the problem in terms others care about, and make the right path the easy one. A mandate alone gets ignored. See [[influencing-without-authority]].

## What does "pre-wiring" key stakeholders mean?

- [x] Talking to them one on one before the big meeting, so concerns surface early.
- [ ] Deciding privately and announcing the result in the meeting.
- [ ] Inviting only people who already agree to the review.
- [ ] Sending the slides an hour before the meeting.

**Why:** Nobody likes being surprised in a group. Early conversations surface objections while they're cheap to address — without turning into backchannel decisions. See [[influencing-without-authority]].

## When is using direct authority appropriate?

- [x] During a security incident or an outage in progress, with clarity about who decides.
- [ ] Whenever you're confident you're right about a design.
- [ ] Whenever a team disagrees with you twice.
- [ ] Never; principal engineers should only influence.

**Why:** Some situations need a clear decision-maker. Afterward, return to collaborative influence. See [[influencing-without-authority]].
