# Quiz: Hero Culture

## A five-person startup has one specialist for a reporting job that rarely changes. What should it do?

- [x] Accept that risk knowingly, and first fix single points on the release path.
- [ ] Rotate all five engineers through the reporting job now, before any other work.
- [ ] Ignore the bus factor until the specialist actually hands in notice.
- [ ] Hire a second specialist so the job always has a backup.

**Why:** The goal isn't a bus factor above one everywhere. It's knowing where yours is one and choosing which of those risks you'll live with. See [[hero-culture]].

## Priya is the only person who can fix the reconciliation job. What change spreads the knowledge?

- [x] Have someone else drive the next fix while Priya only answers questions.
- [ ] Ask Priya to write a long wiki page about the job, then move on.
- [ ] Give Priya a bonus for every fix she makes, so she stays motivated to keep fixing it.
- [ ] Move the job to a different team, with no handover period.

**Why:** Make the hero a teacher, not a fixer. It's slower the first time. The hard part is incentives, so make teaching an explicit goal in the hero's review. See [[hero-culture]].

## Why can hero culture make the data look better than reality?

- [x] The hero fixes problems before anyone logs them as incidents.
- [ ] Incident tools only count outages that page the whole team.
- [ ] Dashboards stop updating correctly whenever the hero is the one on call.
- [ ] Teams with heroes genuinely have fewer incidents to report.

**Why:** Quiet rescues never reach a postmortem, so broken systems look healthy. Turn every rescue into a fix: a runbook, an alert, or a simpler system. See [[hero-culture]].
